Capital OS hosting request

For PL Infra · from PL Capital (Juan Benet) · 28 September 2026

Capital OS is PL Capital's fundraising tool. The team of about ten people uses it for the LP pipeline, research on prospective investors, and raise strategy across our vehicles. Today it runs on a single Mac. We'd like to run it as one LabOS app, with limits a little above the kit defaults. Below are a short summary of the architecture, the specific ask, and a few questions.

Architecture summary

  • One container. A Next.js 16 server (next start, Node) built from the LabOS kit Dockerfile. It serves the pages and the server actions. Heavy imports run in one child process, so pages keep answering while a job writes. A timer inside the same process runs the daily syncs and the backup.
  • One database. Postgres through the kit's provisioned database, reached over TLS with the certificate verified against the RDS CA bundle. It holds all app data. Size today: about 640 MB.
  • One disk. A persistent volume for about 2 GB of working files: research outputs, import files, the feedback journal and a run log.
  • Sign-in. LabOS only. The server forwards the LabOS token to /me, never stores or logs it, and maps the uid to an app user. Anyone with access to the app can read.
  • Outbound calls. Read-only API syncs from Affinity and Linear. Research runs through the Anthropic API. Its web search and fetch run on Anthropic's side, so the container needs no general internet access. The app sends no email or messages and writes nothing to the outside systems.
  • Deploys. The kit flow, with an owner approval each time. We build the image from a clean git archive of a tested commit, and the build fails if any data file would be included. GET /health returns 200. No X-Frame-Options header, so it embeds in os.pl.xyz.

Secrets and backup keys

  • App secrets are env vars entered through the LabOS secrets page: the Affinity, Linear and Anthropic API keys, and one token for the developer feedback export. They are never logged.
  • Backups are encrypted before upload to a GPG public key. The container holds only the public key. The private key that decrypts them stays offline with the owner, plus one sealed copy. The bucket's own KMS encryption sits underneath.
  • Question: does PL already run a secrets store (Infisical, AWS Secrets Manager or similar) we should use for the keys and the backup key's escrow copy, instead of the LabOS page and our own password manager?

Questions for PL Infra

  1. Can one LabOS app get the limits above, with a persistent volume? If not, is the VM fallback possible?
  2. For the provisioned Postgres: which major version, what backups or point-in-time recovery, and what retention? Is its certificate from the standard RDS CA?
  3. Who at PL can access the database, the logs (CloudWatch) and the volume? The data is confidential fundraising data (investor names, pipeline, notes). It's fine for it to be visible to PL Infra staff who need it.
  4. Can you provide an S3 bucket with KMS encryption, that the app can write to and prune (we thin old backups by age), but not list anything else?
  5. Do you have a secrets store we should use (see above)?
  6. Which region, and do outbound calls leave from fixed IPs? Affinity may need them allow-listed.
  7. Is a longer-lived deploy token for a single app possible?

Timing

The app, the Dockerfile and the move-over scripts are ready. The move-over has been rehearsed on a copy of the real data: dump 15 s (200 MB), restore 40 s, 119 tables and 1.2M rows checked table by table. Once the limits are in place, we deploy a test build first, rehearse the move once against the provisioned database, then move over in one evening. The Mac copy stays untouched for a week as the rollback.
