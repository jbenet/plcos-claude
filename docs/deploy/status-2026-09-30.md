### Added tonight (this branch)

- **[service.env.example](service.env.example)** lists every variable the service reads, by name only.
  Each one is tagged required, required once real, later, optional, set by the image, internal, or must
  stay unset. A property fails the gate when the code reads a variable the template doesn't list.
- **`scripts/preflight.sh [--dry]`** checks a target machine against the plan. It covers the environment
  (names only), Node, child processes and worker threads, memory and CPU (the container's cgroup limits
  first), the volume's size, free space and write access, and the tools (`pg_dump`, `pg_restore` and
  `psql` 17, `gpg`, `aws`). It also checks the RDS CA files and the database: version, TLS,
  CREATE privilege, ownership (cutover's freeze needs it) and table count. Without `--dry`, it also tests
  S3 put/list/delete, egress to the three API hosts, and a 401 from LabOS `/me`.
  **Dry run on this Mac against the invented test cluster, with the Mac's system CA bundle standing in
  for the RDS one: every check passed except `aws`, which is not installed here (a warning in a dry
  run).** A decoy value in a forbidden variable failed the check, and
  the value never appeared in the output.
- **`scripts/backup-service-restore.sh`** restores a service backup into an empty database and an empty
  folder. It refuses anything that isn't empty. There was no restore path for the S3 backups before this.
- **`scripts/service-drill.sh`** runs backup → restore on invented demo data (test cluster :5434). It uses
  a throwaway key made with rev 3's exact `gpg --quick-gen-key` command. **Result: PASS.** The backup
  script (dry, `BACKUP_KEEP_DIR`) produced a 153 KiB database file and a 260 KiB files archive, both
  encrypted. The restore took 1 s. `pg-verify` said MATCH: 119 tables, 1,086 rows, 6 sequences and every
  object count. All working files' SHA-256 matched. The restore refused a non-empty database and a
  non-empty folder. Preflight accepted the public key and refused the private one. Everything was
  dropped afterwards.
- **`scripts/cutover-files.sh list|pack`** is runbook step 3c as a script. It packs the working files for
  the volume and leaves out the database folders, `dakota/`, logs, rehearsals, backups and snapshot
  copies. It also leaves out the six research-export files, because today's
  `enrich/identity-review.jsonl` is built with Dakota contact titles and LinkedIn links
  (`lib/enrich/identity-review-export.ts`), and the runbook regenerates those files on the service from
  the stripped database anyway. It reads the archive back and refuses it if anything excluded got in.
  A property covers it on an invented tree.
- The gate passes: types, boundaries, and 1,394/1,394 properties on PGlite and 1,403/1,403 on Postgres,
  five of them new.
- `backup-service.sh` gained `BACKUP_KEEP_DIR`, used only in a dry run, for the drill. In the runbook, §1
  now says 6 GiB and names the template, and §3c names the pack script.

## Blocked on PL Infra's answer

From the ask, still open:
1. Can one LabOS app get 6 GiB, 2 vCPU, a 20 GB persistent volume and permission to spawn a child
   process? If not, can we have the VM fallback (2 vCPU, 8 GiB, 100 GB, Ubuntu)?
2. For the provisioned Postgres: which version, what backups and point-in-time recovery, what
   retention, and is its certificate from the standard RDS CA?
3. Who at PL can reach the database, the logs and the volume?
4. Can we have an S3 bucket with KMS, where the app can write, list and delete under its own prefix?
5. Is there a secrets store (Infisical, AWS Secrets Manager) we should use instead of the LabOS page?
6. Which region, and do outbound calls leave from fixed IPs (for an Affinity allow-list)?
7. Can this one app get a longer-lived deploy token?

New tonight, and the ones that block cutover day itself:
8. **How do we reach the database and the volume on cutover evening?** `cutover.sh` runs `pg_restore`
   from the Mac into the target. Either the Mac needs a network path to the database, or we need a shell
   in the container to run it there after uploading the dump (190–222 MiB). Separately, 2.1 GB of working
   files has to land on the volume, and no mechanism for that exists yet.
9. **A second database, or CREATE DATABASE.** The runbook's first boot runs the demo against the
   provisioned database, but `cutover.sh` restores only into an empty one. So we need a separate demo
   database (or the right to create one), or we have to empty it before cutover.
10. **The kit's database user.** Which variable names carry the URL and the password? Does the user own
    the database? The cutover's freeze, and the 8.5-minute strip that holds the target read-only, both
    need `ALTER DATABASE`. So far `cutover.sh` has only run as a superuser, on the test cluster.
11. **The build.** How does the kit receive the source: a pushed repo, or an uploaded context? Our
    guarantee that no data gets in rests on building from `git archive`. Also, does Kaniko get 4 GiB and
    outbound access to Debian, PGDG, npm and the RDS trust store? The Dockerfile fetches from all four.
